Integration flow and status handling | Disperso API Skip to main content Disperso API Guide API Reference Changelog English Español English Back to Disperso Introduction Authentication and security Global statuses Integration flow Transfers by country Chile Peru Mexico Integration flow On this page Integration flow and status handling Integrating with Disperso requires the merchant to implement adaptive processing logic. Because of the operational dependencies with the banking platforms, the result of a transaction is not always immediate. For this reason, the merchant's system must be prepared to handle asynchronous responses. Response scenarios ​ When making a request, the API can return two main types of flow: Immediate resolution: the transaction finishes in real time with a success or error status. In this case, the flow concludes with the initial response. Deferred resolution ( BANK_PROCESSING ): if the banking platform cannot confirm the operation instantly, the API returns the BANK_PROCESSING status. Implementing the polling loop ​ In deferred resolution cases, it is the merchant's responsibility to implement a polling loop to verify the final status of the transaction. Process: the system must make periodic requests to the status query endpoint until it obtains a definitive result (success or error). Recommended frequency: apply a 5-minute backoff between queries and repeat until you obtain a final status ( DONE or DONE_WITH_ERRORS ). Key note Implementing this polling loop is critical to guaranteeing the integrity of the information and ensuring the end user receives the correct confirmation of their payment or transfer. Polling is the official mechanism Today the result confirmation is obtained exclusively through polling ; the API does not send webhook-style notifications. If your query window expires without a final status, keep the operation as pending and query again later: never assume a rejection just because you did not get a response in time. If the query returns code 1028 If when querying the status you receive this response: { "code" : "1028" , "message" : "Payment order not exist" } it means the order was never registered (the request was lost) and therefore the payment was not made . In that case you must re-send the payment with a POST using the same clientPaymentId to complete it correctly. Because clientPaymentId is idempotent per account, reusing it is safe: if the payment did exist, the API would respond with the duplicate error ( HTTP 400 ); the 1028 confirms the order was not created. REST is a protocol for web services that enables agile development using technologies such as HTTP and JSON. The Disperso REST API gives you a variety of operations and resources to: Create and manage payment orders addressed to beneficiaries. Query the status of payment orders. Make online payments securely and quickly. Service base URL ​ All API endpoints are available under the following base URL: https://api.disperso.com This URL is the same for the production and sandbox environments. The difference between the two environments is determined solely by the authentication token used in each request. Data conventions ​ To integrate correctly, keep in mind the format of the data the API sends and returns: Dates and times: in ISO 8601 format and expressed in UTC . Date fields do not include the time zone suffix ( Z ) or an explicit offset, but they always correspond to UTC. Precision varies by field: creationDate includes fractional seconds, for example 2026-09-16T20:59:23.193531564 . dateTransfer is returned without fractional seconds, for example 2025-09-01T11:21:21 . Amounts: expressed in the major unit of the currency (not its minor unit). The number of decimals depends on the country's currency: Currency Country Allowed decimals CLP Chile No decimals (whole amounts) PEN Peru Up to 2 decimals MXN Mexico Up to 2 decimals accountNumber : a numeric value (no dashes or separators). Send only the account digits. Versioning ​ This API is currently on its first stable version and is subject to continuous improvements and updates aimed at optimizing its functionality. The development team constantly works to add new features and improve performance, ensuring the API stays efficient and relevant. Change history Every new version or change is detailed in the Changelog with its corresponding date, so you can easily adapt your integration to the latest improvements.
